# ProjectAssessmentSpec v2: количество кейсов принадлежит 4К

Статус: draft реализации в учебном боте. Решение владельца: сообщение
от 23.11.2026 «количество кейсов определяется самой спецификацией», затем
«исправляем». Публикация в общий контур этим документом не разрешается.

## Контракт

- Новый мастер `/new_spec` выбирает опубликованную конфигурацию 4К и собирает
  только локальные условия проекта. Число кейсов не запрашивается.
- Новый локальный snapshot имеет `schema_version=2` и не содержит
  `required_case_count`. Колонка БД хранит `NULL` для таких версий.
- Telegram-прогресс читает `completed`, `required` и `remaining` из Channel API 4К.
  До подготовки Cycle число кейсов показывается как ещё не определённое 4К.
- Опубликованные snapshots v1 и назначения остаются неизменными и читаются с
  прежним положительным `required_case_count`. Новый код не переносит и не
  пересчитывает исторические значения.
- В снимке назначения нового формата поле `assessment_spec.required_case_count`
  отсутствует; для v1 оно сохраняется. Остальная схема educational context v1
  остаётся совместимой с текущим adapter 4К.

В 4К число кейсов становится известно из маршрута конкретного Cycle. Выбор
AssessmentConfiguration в боте сам по себе не сообщает фиксированное число.
Отсутствие канонического progress до Cycle не заменяется локальным числом.

## Внедрение и восстановление

Миграция `0013_optional_case_count` только снимает `NOT NULL`; существующие строки,
check `required_case_count > 0` и защита опубликованных версий сохраняются.
Код, понимающий v1/v2, разворачивается вместе с миграцией. При откате приложения
новые v2-строки сохраняются: сначала вернуть совместимый код; downgrade до
`0012_opaque_subject` допустим только если v2-строк с `NULL` нет.

Проверить: новый мастер без вопроса о числе; v2 snapshot/назначение с `NULL`;
v1 readback и неизменность; progress Telegram из 4К; изолированная PostgreSQL
интеграция. Выпуск и CI — отдельный gate.
