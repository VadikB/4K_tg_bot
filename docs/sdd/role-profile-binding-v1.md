# SDD: сопоставление учебной роли с RoleProfileVersion 4К v1

Статус: `DRAFT`, реализовано только в изолированной ветке бота. Общий контур 4К,
merge и deploy ожидают решения product owner о рисках интеграции.

## Разделение ответственности

- Бот владеет каталогом пяти учебных CRISP-DM-ролей версии `2026.1`, локальными
  published-снимками и назначениями участников. Эти роли не создаются в 4К.
- 4К владеет опубликованными `RoleProfileVersion`, AssessmentProgram, Cycle и
  оцениванием. Его `get_published_role_profile(version_id)` служит read-only
  проверкой ID/checksum, а `educational-contexts/prepare` повторно проверяет
  сохранённую ссылку при допуске.
- Сопоставление в боте — отдельный неизменяемый артефакт с версиями. Оно не меняет
  published-снимок учебной роли и не переназначает студента.

## Сценарии

1. Администратор-создатель проекта выбирает каталожную роль и точные ID/checksum
   опубликованной `RoleProfileVersion` 4К. `/map_role PROJECT ROLE PROFILE_ID CHECKSUM`
   проверяет ссылку через адаптер вне DB-транзакции, повторно проверяет состояние
   роли внутри транзакции и публикует новую версию сопоставления. При недоступном
   4К или несовпадении checksum ничего не публикуется. Повтор той же команды
   возвращает существующую последнюю версию.
2. Участнику можно назначить учебную роль до сопоставления. `/assign_assessment`
   остаётся закрытым, пока нет встроенной legacy-ссылки или опубликованного
   сопоставления. Созданное назначение оценки закрепляет точный
   `role_profile_binding_id`; следующая версия сопоставления не меняет его.
3. `/publish_context` формирует прежний `schema_version=1` snapshot из
   опубликованной учебной роли и закреплённого сопоставления. Для старых
   назначений с `role_profile_binding_id=NULL` используются только ранее
   опубликованные встроенные ID/checksum версии роли. 4К получает прежние поля
   `role.agent4k_role_profile_version_id` и
   `role.agent4k_role_profile_checksum`; новый API 4К не нужен.

## Инварианты и совместимость

- Одна версия сопоставления относится к одной точной `ProjectRoleVersion`.
  Исправление делает новую версию; опубликованная строка защищена trigger от
  UPDATE/DELETE. FK назначения на версию сопоставления также защищён от UPDATE.
  Новые оценки выбирают последнюю версию, старые сохраняют ссылку.
- Команда не создаёт `RoleProfileVersion` в 4К и не подбирает профиль по имени.
  Программная совместимость и questionnaire/profile admission остаются проверками 4К.
- Бот не переписывает опубликованные контексты или уже созданные Cycle. Их
  `assignment_ref` и checksum остаются неизменными.
- Миграция `0010_role_profile_bindings` добавляет таблицу и nullable FK к
  `assessment_assignments`; старые строки не переносятся и сохраняют прежний
  путь чтения. Downgrade допустим только пока опубликованных привязок нет.
- Команда доступна только владельцу проекта. Это локальная проверка для новой
  операции, не свидетельство полной изоляции остальных admin-команд.

## Приёмка и ограничения выпуска

- [x] Локальное назначение до mapping не создаёт оценку.
- [x] Проверенная привязка открывает назначение оценки без изменения учебной роли.
- [x] Старая оценка остаётся на прежней версии после публикации новой привязки.
- [x] Старые назначения со встроенной ссылкой продолжают работать.
- [x] Изменение опубликованной привязки отвергается PostgreSQL.
- [ ] Реальный 4К endpoint и общий Telegram-контур проверены после решения PO.
- [ ] Выбор подходящей `RoleProfileVersion` в UX без ручного ID/checksum —
  отдельная задача; текущая команда рассчитана на подготовленного администратора.

## Откат

До публикации привязок — вернуть код и downgrade `0010 -> 0009`. После публикации
не удалять привязки и не выполнять downgrade: отключить `/map_role` и новые
назначения, сохранить ссылки и подготовить отдельный компенсационный релиз.
