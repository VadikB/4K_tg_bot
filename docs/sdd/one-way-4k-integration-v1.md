# Предложение: односторонняя связь бота с 4К через тестовую Organization

Статус: `DRAFT`, обновлён 18.11.2026. Контракт не реализован и не разрешает включение
общего Telegram-канала. Решение владельца: максимум учебных данных хранится в БД
бота; бот инициирует обращения к 4К через тестовую Organization. Данные оценки
и её методология принадлежат 4К.

## Владение и направление

| Данные или действие | Владелец |
| --- | --- |
| Telegram ID, username, введённые администратором ФИО и email, приглашение, членство, проекты, учебные роли и их назначения | БД бота |
| Связь локального участника с внутренним пользователем 4К, статус отправки и точные внешние ссылки | БД бота |
| Organization тестового контура, RoleProfileVersion, Questionnaire, PersonalizedProfile, AssessmentProgram, Cycle, AS/Dialogue, Results | 4К |
| Неизменяемый assessment context, необходимый для воспроизведения начатой оценки | 4К, точная разрешённая копия на момент допуска |

Запросы идут только `бот → 4К`; ответы 4К возвращаются боту для показа в Telegram.
4К не вызывает webhook бота и не редактирует его проект/участника. Результат
оценки не вычисляется в боте. Доступ студента проверяется по его Telegram ID
локально до каждого вызова 4К.

## Требуемая замена email-моста

Текущий `POST /integration/v1/participants/resolve` принимает email и имя.
Решение владельца от 18.11.2026: email хранится только в БД бота. Вызов этого
endpoint из бота отключён также для старых приглашений. Предлагается отдельный
versioned service endpoint `POST /integration/v1/subjects/resolve`:

```json
{
  "source_system": "telegram_student_bot",
  "external_subject_ref": "<случайный непрозрачный идентификатор>",
  "organization_ref": "<согласованная тестовая Organization>"
}
```

Успешный ответ: `agent4k_user_id` (внутренний положительный ID 4К) и
`status` (`existing` или `provisioned`). Повтор того же ключа в той же Organization
возвращает тот же ID; попытка перенести уже связанный ключ в другую Organization
возвращает конфликт без изменения данных. `external_subject_ref` создаёт и хранит
бот, он не выводится из Telegram ID, email или ФИО. В запросе и ответе нет
Telegram ID, username, email или имени. 4К хранит только соответствие
`(source_system, external_subject_ref, organization_ref) → user_id`, необходимое
для своих FK. Выдуманный email не используется. Точный формат ответа, HTTP-код
конфликта и способ создания внутреннего пользователя требуют проверки схемы 4К.

После ответа бот закрепляет внутренний ID в своей БД и передаёт его через
действующий immutable assessment context. `assignment_ref` и checksum связывают
конкретный локальный Assignment с Cycle 4К. Дальше бот читает каноническое
состояние и отправляет действия по существующему Channel API. Технический
timeout повторяется с тем же idempotency key; при недоступности 4К бот не
подменяет оценку локальным расчётом.

Текущий `educational-contexts/prepare` выводит Organization из
`course.external_id` и при необходимости создаёт её. Для одной заранее выбранной
тестовой Organization этот участок потребуется адаптировать: разрешать только
утверждённый scope и сохранять курс/поток как данные контекста бота, не создавать
новую Organization при каждом новом `course.external_id` неявно.

## Совместимость и допуск

Старые приглашения сохраняют локальный путь принятия. Уже сохранённые
`agent4k_user_id` остаются доступными, но новые связи по email не создаются.
Новый endpoint может использоваться для любого ещё не связанного участника после
принятия контракта и миграции локального `external_subject_ref`.
Выбранная тестовая Organization должна быть явно зафиксирована и изолирована
от рабочих данных. До реализации endpoint и проверки соответствия существующему
`users`/Organization, а также до решения о рисках Telegram Student Channel,
участник без ранее сохранённого `agent4k_user_id` может вступить в проект, но не
получать оценочные назначения.

Открытые решения для отдельной implementation-задачи: точный ID/код тестовой
Organization и её жизненный цикл; контракт `external_subject_ref` и реакция на
повтор/конфликт; создание технического пользователя 4К без email; политика
удаления тестового контура. Эти решения требуют review технического владельца
4К и product owner перед включением интеграции.
