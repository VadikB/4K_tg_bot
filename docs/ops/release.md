# Выпуск Telegram-бота после слияния PR

## Правило

Каждый PR в `main`, меняющий исполняемый код, зависимости, миграции или артефакты
бота, требует выпуска на сервер. Ответственный за слияние доводит выпуск до
проверенного результата либо сообщает о неудаче и выполняет откат. Слияние само
по себе не доказывает, что сервер обновлён. Изменения только документации не
требуют перезапуска сервиса; это явно отмечается в PR.

В отчёте о выпуске фиксируются SHA слитого commit, SHA установленного кода,
время и результат CI, версия миграции до и после, состояние сервиса и результат
проверки бота. Пока эти сведения не получены, статус выпуска — `PENDING`.
Проверенный выпуск имеет статус `DEPLOYED`; неудачный — `FAILED` с причиной и
сведениями об откате. Следующий PR не должен маскировать незавершённый выпуск.

## Порядок

1. До слияния: проверить зелёный CI, состав миграций и способ отката. Для
   изменения схемы подготовить резервную копию БД и проверить возможность её
   восстановления. Не включать интеграцию с 4К без отдельного решения.
2. После слияния: взять точный SHA `main` и собрать из него выпуск без `.env`,
   `.venv`, `.git`, секретов и пользовательских данных. Проверить checksum
   выпуска до переноса на сервер.
3. На сервере: сверить текущий выпуск и миграцию; сохранить предыдущий код.
   Выполнить необходимые миграции, установить проверенный выпуск и перезапустить
   `4k-tg-bot.service`. Серверный `.env` и runtime `.venv` сохраняются. При
   изменении зависимостей обновить их по проверенному составу выпуска.
4. Проверить `ActiveState=active`, `SubState=running`, отсутствие новых сбоев,
   установленный SHA и доступность базовых команд Telegram. Проверка предметной
   интеграции с 4К проводится только при отдельном допуске.
5. При сбое вернуть сохранённый код и перезапустить сервис. Откат миграций,
   затрагивающих данные, выполнять только по заранее согласованному плану.

## Текущее состояние и ввод автоматизации

На 20.11.2026 серверный сервис работает из
`/home/vadim_bogachev/projects/4K_tg_bot` на ветке
`codex/tg-server-migration` (`f7c5d54`), поверх которой есть 16 изменённых
отслеживаемых файлов от прошлых ручных выпусков. `main` после PR #1 содержит
`f526c93`, но этот код на сервер ещё не установлен. Прямой `git pull` в такой
рабочей копии не является безопасным способом выпуска.

До включения автоматического запуска после merge нужно один раз перевести
сервер на выпуск из неизменяемого Git commit с сохранением существующих `.env`,
`.venv` и БД; сверить старый код с `main`; проверить миграции, резервную копию,
запуск и откат. После этого настроить отдельный доступ CI к серверу и проверить
выпуск и откат на тестовом изменении. До завершения этого перехода обновление
после merge выполняется контролируемым операторским выпуском по порядку выше.
