# TASK-022: видимость проектов по административной роли

## Решение и граница

Решение владельца от 19.11.2026: суперадминистратор видит все проекты, обычный
администратор проекта — только проекты, созданные им. Участник без системной роли
видит проекты своего участия. `/projects` и `/my_projects` используют одну
авторизованную выборку. Создание и изменение проектов, участники, роли и оценка
не меняются этим slice.

## Реализация и совместимость

- `SUPERADMIN_TELEGRAM_IDS` используется только для первоначального назначения
  системной роли `superadmin` в БД бота. Суперадмин также получает `admin` для
  существующих административных команд. Выданные роли не отзываются изменением
  конфигурации.
- `list_projects` сначала проверяет сохранённую роль `superadmin`, затем `admin`.
  Суперадмину возвращаются все проекты, администратору — только
  `created_by_user_id = actor.id`, участнику — проекты его участия. Неактивный
  аккаунт не получает список.
- `/start` показывает фактическую административную роль и соответствующее
  значение `/projects`. Настройка добавлена в `.env.example` и `README.md`.

## Проверки и откат

Регрессия: два владельца создают разные проекты; каждый видит только свой,
суперадмин видит оба и свой, участник без членства не видит ничего. После
повторного создания сервиса без bootstrap-настроек суперадмин сохраняет доступ
через запись в БД. Unit проверяет парсинг настройки и меню.

Локальный минимум на текущем незакоммиченном diff:

- `.venv/bin/ruff check .` → PASS.
- `.venv/bin/mypy app` → PASS, 18 source files.
- `.venv/bin/pytest -q -m 'not integration'` → PASS, 73 теста.
- `TEST_DATABASE_URL=…/tg_visibility_pytest .venv/bin/pytest -q -m integration`
  → PASS, 22 теста на отдельной PostgreSQL 16; временный контейнер удалён.
- `git diff --check` → PASS.

CI, реальный Telegram API, PR, merge и deploy — NOT_RUN. Поэтому наблюдаемое
поведение запущенного бота изменится только после его согласованного выпуска.
Откат до выпуска — вернуть код и настройки; роль `superadmin` в БД можно оставить
неактивной для прежнего кода. После выпуска отзыв прав требует отдельной
административной операции, не удаления данных проектов.

Стоп-условия: предметная норма — нет; публичный API 4К — нет; изменение схемы БД —
нет; потеря данных — нет. Авторизация изменения списка дана сообщением владельца.
