# TASK-003: участники и одноразовые приглашения

## Результат

Администратор добавляет участника в проект, получает одноразовую Telegram deep link,
а студент по ссылке связывает свой `telegram_user_id` с участником проекта.

## Область

- Включено: pending participant, безопасный токен, TTL, принятие приглашения,
  защита от повтора, список участников, аудит и миграция.
- Не входит: email-доставка, массовый импорт, отзыв приглашения, CRISP-DM-роли,
  спецификация оценки и API 4К.

## Источники и решения

Повторно использованы источники TASK-001/002 и решение владельца «делаем» от
06.11.2026. Base commit `ed88877304d7ee7877e96b659761248702ddb735`.
Бот владеет membership; предметные данные оценки не меняются.

Изменение кардинальности согласовано исходной схемой: участник заводится администратором
до первого входа в Telegram. `user_id` становится nullable только для статуса `invited`;
после принятия сохраняются `active`, `joined_at` и одноразовый `used_at`.

Стоп-условия: все `нет`. Миграция обратно совместима. Downgrade разрешён только при
отсутствии непринятых приглашений, иначе останавливается без удаления данных.

## Критерии приёмки

- [x] Только администратор может создать приглашение и прочитать список.
- [x] В БД хранится SHA-256, сырой токен возвращается один раз.
- [x] Истёкшее и повторное приглашение отклоняются.
- [x] Принятие атомарно связывает Telegram user и участника проекта.
- [x] Участник после принятия видит проект через `/projects`.
- [x] Миграция проверена поверх существующей и чистой БД.
- [ ] Реальная Telegram deep link проверена с токеном бота.
