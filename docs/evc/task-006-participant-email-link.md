# TASK-006: email-связь участника с 4К

## Результат

Новое приглашение участника содержит нормализованный email. После принятия ссылки
участник сохраняет локальную Telegram-идентичность, а nullable `agent4k_user_id`
зарезервирован для результата будущего сервисного API 4К.

## Область

- Включено: email в мастере приглашения, нормализация, уникальность внутри проекта,
  nullable связь с внутренним ID 4К, миграция, аудит без значения email и тесты.
- Не входит: создание/поиск пользователя в 4К, подтверждение владения email,
  организация, профиль, Assessment Cycle, выдача Case и показ итогового результата.

## Источники и решения

- Решение владельца от 06.11.2026: email допустим как технический мост к существующей
  пользовательской модели 4К; один email может участвовать в нескольких проектах.
- Base: `7e23eef835d76be633ac715845f059af6594f638`.
- Прочитаны обязательные документы 4К: `README.md`, `CONTRIBUTING.md`,
  `docs/evc/agent-workflow.md`, `verification-matrix.md`, `artifact-recipe.md`,
  архитектурный context/registry, Change 01, manifest, ADR-002 и traceability.
- Email не входит в snapshot проекта/роли/оценки и не записывается в audit payload.
- Существующие строки мигрируют с `email=NULL`; обязательность действует на новые
  приглашения. Это сохраняет совместимость без выдуманного адреса и без изменения PII.

## Критерии приёмки

- [x] Новое приглашение без корректного email отклоняется.
- [x] Email нормализуется и уникален внутри проекта.
- [x] Один email допустим в разных проектах.
- [x] Принятие Telegram-ссылки не выдаётся за подтверждение email в 4К.
- [x] До интеграции `agent4k_user_id` и `agent4k_linked_at` отсутствуют.
- [x] Миграция сохраняет существующих участников без подстановки данных.
