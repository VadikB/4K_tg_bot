# 4K TG Bot

Telegram-бот учебных проектов по CRISP-DM с подключением оценки 4К.

Проект хранит учебные проекты, участников, версии проектных ролей, спецификации
оценки и назначения. Предметная оценка 4К остаётся во внешнем сервисе и вызывается
через адаптер; бот не рассчитывает уровни компетенций самостоятельно.

## Статус

Работают административные пути карточки проекта и участников: bootstrap-администратор
регистрируется по `/start`, создаёт проект, выпускает одноразовую ссылку участнику,
а участник связывает Telegram identity с проектом через эту ссылку. Для нового
приглашения администратор выбирает проект из списка, затем указывает ФИО, email
и Telegram ID. Ссылка принимается только этим аккаунтом. Прежние
email-приглашения продолжают работать. Email
остаётся только в БД бота. Для ограниченного test-сценария оператор связывает
участника с 4К по случайному UUID; ФИО, email и Telegram ID не передаются.
Интеграция с 4К по умолчанию выключена. В режиме `mock` разрешены только локальная
разработка и тесты: он подключает HTTP-клиент к явно указанному loopback-стабу
(`AGENT4K_API_URL=http://127.0.0.1:...`), без локальной предметной имитации 4К.

Draft Telegram-канал студента описан в
[`docs/sdd/student-channel-v1.md`](docs/sdd/student-channel-v1.md). `/get_case`
(`/case` остаётся алиасом), `/progress` и `/case_status` читают 4К через adapter;
бот хранит только техническую привязку
текстового ответа и не рассчитывает Case или прогресс. До решения по рискам
интеграции канал остаётся выключенным в общем контуре.

## Быстрый старт

```bash
/usr/local/bin/python3.12 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
docker compose up -d db
alembic upgrade head
python -m app.main
```

Добавьте Telegram ID администраторов проектов в `BOOTSTRAP_ADMIN_TELEGRAM_IDS`,
а ID пользователей, которым разрешён просмотр всех проектов, — в
`SUPERADMIN_TELEGRAM_IDS`. При первом `/start` бот сохраняет роль `admin` для
администратора проекта и обе роли — для суперадмина — в своей БД. Изменение
списка bootstrap ID не отзывает уже выданные
роли: их отзыв требует отдельной административной операции. Токен бота хранится
только в `.env`.

## Команды администратора

```text
/start        регистрация и определение прав
/new_project  пошаговое создание карточки проекта
/projects     проекты, созданные вами; суперадмину — все проекты
/add_participant  выбрать проект и пригласить по ФИО, email и Telegram ID
/participants CODE  участники проекта
/feedback PROJECT_CODE  отправить отзыв преподавателю проекта
/link_4k CODE  проверить существующую связь с 4К
/roles        пять фиксированных ролей CRISP-DM
/roles PROJECT  версии ролей проекта (администратор)
/map_role PROJECT ROLE PROFILE_ID CHECKSUM  связать учебную роль с профилем 4К
/assign_role  выбрать проект, участника и роль из списков
/my_roles     роли текущего участника
/new_spec     создать draft спецификации оценки
/publish_spec PROJECT  опубликовать локальный snapshot
/specs PROJECT  версии спецификации
/assign_assessment PROJECT PARTICIPANT_ID ROLE  назначить оценку
/publish_context ASSIGNMENT_ID  опубликовать неизменяемый контекст назначения
/prepare_cycle ASSIGNMENT_ID  зарегистрировать контекст в 4К и проверить admission
/admission_programs ASSIGNMENT_ID  показать совместимые опубликованные программы
/connect_program ASSIGNMENT_ID PROGRAM_ID  явно подключить выбранную программу
/progress     прогресс участника
/case_status [ASSIGNMENT_ID]  готовность текущего кейса без оценки времени ожидания
/get_case [ASSIGNMENT_ID]  получить или продолжить кейс после назначения оценки
/cancel       отмена текущего диалога
```

`/feedback PROJECT_CODE` доступна подключённому участнику в личном чате с ботом.
Следующее текстовое сообщение бот отправляет администратору, создавшему проект.
Отзыв не передаётся в 4К и не сохраняется в базе бота. При неподтверждённой
доставке бот сообщает об этом без автоматического повтора.

`/assign_role` вызывается без аргументов в личном чате администратора. Бот
показывает кнопки с доступными кодами проектов, затем ID участников выбранного
проекта и коды опубликованных ролей. Значения выбираются нажатием; вводить их
в команду не требуется.

Bootstrap не делает все новые аккаунты администраторами: право получает только
точный `telegram_user_id` из `BOOTSTRAP_ADMIN_TELEGRAM_IDS` или
`SUPERADMIN_TELEGRAM_IDS`. Обычный администратор в `/projects` и `/my_projects`
видит только проекты, которые создал сам. Суперадмин видит все проекты. Участник
без административной роли видит проекты своего участия.

Пригласительный токен действует `INVITATION_TTL_HOURS`, показывается только при
создании ссылки и хранится в PostgreSQL только как SHA-256. Повторное или истёкшее
приглашение отклоняется в транзакции. Новый мастер показывает список проектов,
в которые можно пригласить участника, затем запрашивает ФИО, email и числовой
Telegram ID; бот не может первым написать этому аккаунту, поэтому
администратор передаёт ссылку самостоятельно. Один Telegram ID может участвовать
в разных проектах, но повторное приглашение в тот же проект отклоняется. Email
обрезается по краям, приводится к нижнему регистру и уникален внутри проекта;
формат адреса бот не проверяет. Введённое ФИО сохраняется при принятии
ссылки, даже если отображаемое имя Telegram отличается. Старые email-приглашения
сохраняют прежний порядок принятия.

Пять ролей текущего семестра определены в проверяемом по SHA-256 каталоге
`app/artifacts/crisp_dm_roles/2026/`. При создании проекта бот публикует их локальные
неизменяемые версии без обращения к 4К. Команды произвольного создания и публикации
ролей удалены из Telegram-интерфейса. Участнику можно назначить несколько ролей;
первая становится основной. Назначение учебной роли само по себе не означает допуск
к оценке: до отдельного сопоставления с опубликованной `RoleProfileVersion` 4К
`/assign_assessment` завершается без создания назначения оценки. Новые проекты
получают стабильный `course_external_id`, общий для проектов одного курса и потока.
`/map_role` выполняет это сопоставление через read-only проверку 4К; каждая
опубликованная версия привязки неизменяема. Назначение оценки закрепляет точную
версию привязки, а новая версия не меняет прежние назначения и snapshots.
Контракт — [`docs/sdd/role-profile-binding-v1.md`](docs/sdd/role-profile-binding-v1.md).
Для уже существующих проектов автоматическое добавление ролей не выполняется.
Оператор может отдельно просмотреть и применить добавление только отсутствующих
ролей одного проекта через `python -m app.catalog_backfill`; конфликтующие старые
версии останавливают всю операцию без записи. Опубликованные версии и назначения
не переписываются.

Пример операционного backfill после отдельного решения о выпуске (в окружении
нужно явно задать `DATABASE_URL`; URL не передаётся аргументом команды):

```bash
python -m app.catalog_backfill --project PROJECT_CODE --actor-telegram-id ADMIN_ID
python -m app.catalog_backfill --project PROJECT_CODE --actor-telegram-id ADMIN_ID \
  --apply --expect-fingerprint FINGERPRINT_FROM_PREVIEW
```

`ADMIN_ID` должен принадлежать активному администратору, создавшему этот проект.
Первый вызов не изменяет БД. Второй требует точный отпечаток просмотренного
состояния; при изменении проекта план нужно получить снова. На рабочей БД этот
шаг ещё не выполнялся.

`/new_spec` показывает доступные проекты и опубликованные конфигурации 4К кнопками.
Бот получает точную ссылку, отпечаток и методологию через сервисный API 4К;
период, число кейсов и получателей результата администратор задаёт как локальные
настройки проекта. Ручной ввод ссылки и checksum конфигурации не требуется.
Локальная спецификация оценки фиксирует выбранную конфигурацию и эти настройки.
Статус `published`
означает неизменяемость локального snapshot, но не runtime-допуск: до проверки через
API 4К snapshot содержит `runtime_admission=pending_agent4k_verification`, а назначение
не получает `external_cycle_id`.

После допуска к назначению оценки команда `/publish_context ASSIGNMENT_ID` фиксирует отдельный
неизменяемый snapshot: курс и поток, учебный проект и этапы CRISP-DM, точную версию
проектной роли и `RoleProfileVersion` 4К, спецификацию оценки и технический
`agent4k_user_id`. Email, Telegram ID и отображаемое имя участника в snapshot не входят.
Стабильный `assignment_ref` предназначен для последующего создания контекста и Cycle в 4К.
Команда `/prepare_cycle ASSIGNMENT_ID` передаёт snapshot в 4К. Пока обязательные
questionnaire, AssessmentProgram и PersonalizedProfile не допущены, бот сохраняет
`awaiting_admission` и показывает точные причины; `external_cycle_id` не создаётся.
После выполнения admission та же команда получает `preparing`, а при завершении
канонической очереди 4К — `prepared` и сохраняет реальный `external_cycle_id`.
Причину `PROGRAM_NOT_CONNECTED` преподаватель может закрыть явным выбором из
`/admission_programs`; бот показывает только программы с тем же `assignment_ref` и
разрешённой RoleProfileVersion. Questionnaire и PersonalizedProfile продолжают
подтверждаться в своих предметных сценариях 4К.

Бот не отправляет email в 4К. Старые email-приглашения принимаются локально,
но прежний `POST /integration/v1/participants/resolve` больше не вызывается.
Ранее сохранённый `agent4k_user_id` остаётся доступен; `/link_4k CODE` показывает
его статус. Для новой связи требуется отдельный сервисный контракт по непрозрачному
ключу, описанный в `docs/sdd/one-way-4k-integration-v1.md` (`DRAFT`).

## Выпуск

Слияние PR в `main` запускает обязательное обновление работающего бота на сервере.
Выпуск считается завершённым только после проверки точного commit, состояния
`4k-tg-bot.service` и короткой проверки команд бота. Порядок и текущие ограничения
описаны в [регламенте выпуска](docs/ops/release.md).

## Архитектурные правила

- `telegram_user_id`, а не username, является идентификатором Telegram.
- Email хранится локально; ключ новой интеграции — случайный UUID.
- Системные права (`admin`, `participant`) отделены от ролей CRISP-DM.
- Один участник может иметь несколько проектных ролей.
- Опубликованные роли и спецификации неизменяемы; изменения создают новую версию.
- Назначение фиксирует точные версии роли и спецификации оценки.
- Участник может получить не более одного нового кейса за локальную дату проекта.
- Ответы и результаты оценки не пишутся в обычные application logs.
- При недоступной интеграции с 4К выдача кейса завершается ошибкой, без встроенной
  предметной подмены.
